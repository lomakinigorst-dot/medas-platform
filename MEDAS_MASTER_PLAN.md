## ЧАСТЬ 1 — Единая модель пользователя {#часть-1}

### 1.1 Концепция: базовый аккаунт + роли

**Ключевой принцип:** в MEDAS нет отдельных типов аккаунтов. Есть один тип — **пользователь (User)**. Дополнительные возможности — это **роли**, которые навешиваются на базовый аккаунт.

Это означает:
- Один телефонный номер = один аккаунт навсегда
- Человек может быть пациентом, владельцем клиники и врачом одновременно
- При входе система определяет, какие роли у пользователя, и показывает соответствующий интерфейс
- Добавление роли не создаёт новый аккаунт — только расширяет права существующего

**Текущее состояние (до миграции):**
```python
class User(Base):
    phone: str  # unique
    name: str
    role: str   # "patient" | "clinic" | "doctor"  ← строка, один вариант
    clinic_id: int | None
    bonus_balance: int
```

**Целевое состояние (после миграции):**
```python
class User(Base):
    phone: str              # unique, первичный идентификатор
    name: str
    roles: list[str]        # ["patient", "clinic_owner", "doctor", "clinic_staff", "superadmin"]
    doctor_id: int | None   # FK → doctors.id (если роль doctor)
    bonus_balance: int
    is_active: bool
    created_at: datetime
    last_login: datetime
```

### 1.3 Техническая реализация (миграция User)

**Шаг 1 — Alembic миграция:**
```sql
-- Добавляем новые поля
ALTER TABLE users ADD COLUMN roles VARCHAR[] DEFAULT ARRAY['patient'];
ALTER TABLE users ADD COLUMN doctor_id INTEGER REFERENCES doctors(id);
ALTER TABLE users ADD COLUMN is_active BOOLEAN DEFAULT TRUE;

-- Заполняем roles из старого поля role
UPDATE users SET roles = ARRAY[role] WHERE role IS NOT NULL;
UPDATE users SET roles = ARRAY['patient'] WHERE role IS NULL;

-- Для пользователей с ролью clinic — добавляем clinic в UserClinic
INSERT INTO user_clinics (user_id, clinic_id, staff_role, is_active)
SELECT id, clinic_id, 'owner', TRUE FROM users WHERE role = 'clinic' AND clinic_id IS NOT NULL;

-- Для пользователей с ролью doctor — привязываем doctor_id
-- (нужна дополнительная логика поиска doctor по phone)
```

**Шаг 2 — FastAPI dependency:**
```python
def require_roles(*roles: str):
    """Декоратор: проверить что у пользователя есть хотя бы одна из ролей"""
    async def checker(current_user: User = Depends(get_current_user)):
        if not any(r in current_user.roles for r in roles):

        return current_user

    user = Depends(require_roles("clinic_owner", "clinic_staff", "superadmin"))

    ...
```

**Шаг 3 — JWT payload:**

### 1.4 Переключение контекста

Если пользователь совмещает несколько ролей (например: пациент + владелец клиники + врач), в header отображается **переключатель контекста**:

```
[ Личный кабинет ▼ ]
  ● Пациент
  ○ Клиника "Здоровье"
  ○ Врач (профиль)
```

**Правила переключения:**
- При входе: если есть роль выше patient — предложить выбрать контекст
- При переключении: URL меняется (`/cabinet/patient` → `/cabinet/clinic`)
- Сохранять выбранный контекст в localStorage
- Уведомления приходят независимо от контекста

**Реализация (frontend):**

### 1.5 Авторизация через звонок (детали)

**Поставщик:** smsc.ru  
**Метод:** входящий звонок, код диктуется голосом  
**Параметры запроса:**
```
POST https://smsc.ru/sys/send.php
  login=...
  psw=...
  phones=+79991234567
  mes=CODE        # смысл не важен — звонок идёт по коду
  call=1          # режим звонка
  voice=w         # женский голос
  fmt=3           # ответ в JSON
```

**Нормализация номера (Python):**
```python
import re

def normalize_phone(raw: str) -> str:
    """
    Принимает: +7XXX, 7XXX, 8XXX, 10 цифр
    Возвращает: +7XXXXXXXXXX
    """
    digits = re.sub(r'\D', '', raw)
    if len(digits) == 10:
        digits = '7' + digits
    elif len(digits) == 11 and digits[0] == '8':
        digits = '7' + digits[1:]
    if len(digits) != 11 or not digits.startswith('7'):
        raise ValueError(f"Invalid phone: {raw}")
    return '+' + digits
```

**Поток авторизации:**
```
1. POST /auth/send-otp  { phone: "+79991234567" }
   → normalize_phone()
   → Генерировать 4-значный код
   → Сохранить в Redis: key="otp:{phone}", value={"code": "1234", "attempts": 0}, TTL=600
   → Позвонить через smsc.ru (call=1)
   → Ответ: { message: "Ожидайте звонок" }

2. POST /auth/verify-otp  { phone: "+79991234567", code: "1234" }
   → Получить из Redis
   → Проверить attempts < 3 (иначе 429)
   → Сравнить код
   → При успехе: удалить из Redis, вернуть JWT
   → При неудаче: инкрементировать attempts
```

**Безопасность OTP:**
- Код 4 цифры → 10000 вариантов → 3 попытки = brute force невозможен
- TTL 600 секунд (10 минут) — достаточно для получения звонка
- Rate limiting на `/auth/send-otp`: не более 3 запросов с одного IP за 60 сек
- Новый запрос OTP перезаписывает старый в Redis

### 1.6 Жизненный цикл аккаунта

```
РЕГИСТРАЦИЯ
    ↓
Ввод телефона → Звонок → Код → Создание User(roles=["patient"])
    ↓
БАЗОВЫЙ ПАЦИЕНТ
    ↓
[Опционально] Заявка на клинику → Верификация → roles += ["clinic_owner"]
[Опционально] Инвайт от клиники → Принятие → roles += ["doctor"]
[Опционально] Инвайт от клиники → Принятие → roles += ["clinic_staff"]
    ↓
РАСШИРЕННЫЙ АККАУНТ (несколько ролей)
    ↓
[Деактивация роли]
    - Врач уходит из клиники: roles остаётся ["doctor"], но без clinic привязки
    - Клиника закрывается: roles -= ["clinic_owner"], клиника помечается is_active=False
    - Аккаунт блокируется суперадмином: is_active=False (все роли недоступны)
    ↓
ДЕАКТИВИРОВАН
    - Данные хранятся (GDPR: 3 года)
    - Вход невозможен
    - Записи архивируются
```

2. 🔍 Вводит специализацию ("кардиолог") или симптом ("боль в груди")
3. 📋 Переходит на `/search?specialty=cardiologist&city=moscow`
4. 👁️ Видит список врачей с карточками: фото, имя, клиника, цена, рейтинг, ближайший слот
5. 🔢 Использует фильтры: цена, район, метро, принимает ДМС, рейтинг ≥ 4.5
6. 👆 Кликает на карточку врача
7. 📄 Открывает `/doctor/[slug]` — полный профиль: биография, образование, отзывы, расписание
8. 📅 Выбирает дату и время → кнопка "Записаться"
9. 🔐 Система перенаправляет на `/login` (если не авторизован)
10. 📞 Вводит телефон → получает звонок → вводит код
11. ✅ Автоматически возвращается к форме записи (URL сохранён в session)
12. 📝 Заполняет: имя, дата рождения, комментарий (опционально)
13. 💳 Выбирает способ оплаты: онлайн / в клинике / бонусами
14. ✅ Запись создана → экран подтверждения

**Действия системы:**
- Сохранить URL страницы до редиректа на логин (localStorage)
- Создать `Appointment(status="pending", service_type="consultation")`
- Отправить SMS/email пациенту: "Вы записаны к врачу X на [дата]"
- Отправить уведомление клинике: "Новая заявка от [пациент]"
- Начислить бонусы: +100 за первую запись

**Риски оттока:**
- Слишком длинная форма записи → оставить только обязательные поля
- Нет свободных слотов на ближайшие дни → предлагать лист ожидания
- Неизвестный сайт → доверие: показывать число записей, верифицированных клиник

**Что нужно для реализации:**
- `GET /search?specialty=&city=&metro=&price_max=&dms=&rating_min=` (есть)
- `POST /appointments` (есть)
- Редирект с сохранением URL (frontend, localStorage)
- Email/SMS уведомления (❌ не реализовано)


### Д8: Отвязка от клиники

**Инициатор — клиника:**
1. Клиника деактивирует врача: `Doctor.is_active=False`
2. Врач получает уведомление: "Клиника X прекратила ваше сотрудничество"
3. `roles` врача НЕ меняются (остаётся `["patient", "doctor"]`)
4. `user.doctor_id` сохраняется (историческая информация)
5. Будущие записи к этому врачу в этой клинике: cancelled + уведомление пациентам

**Инициатор — врач:**
1. Врач: ЛК → "Отвязаться от клиники X"
2. Подтверждение
3. Клиника получает уведомление
4. `Doctor.is_active=False` для этой клиники

**Будущие записи:**
- Если запись через 7+ дней → уведомление пациенту о необходимости выбрать другого врача
- Если запись через < 7 дней → клиника сама связывается с пациентом

## ЧАСТЬ 6 — Сценарии суперадмина MEDAS {#часть-6}

### А1: Рассмотрение заявки на регистрацию клиники

**Дашборд суперадмина `/admin`:**
```
Очередь на рассмотрение:
┌────────────────────────┬──────────────┬──────────┬──────────────┐
│ Клиника                │ Тип заявки   │ Дата     │ Действие     │
├────────────────────────┼──────────────┼──────────┼──────────────┤
│ МедЦентр Плюс          │ Новая клиника│ 14.06    │ Рассмотреть  │
│ СтомаПро (ИНН заявлен) │ Привязка     │ 14.06    │ Рассмотреть  │
└────────────────────────┴──────────────┴──────────┴──────────────┘
```

**При рассмотрении:**
- Просмотр загруженных документов (открываются из MinIO)
- Проверка ИНН в EGRUL (ссылка на сайт ФНС или API)
- Чекбоксы: ✅ ИНН совпадает ✅ Лицензия действительна ✅ Документы полные
- Кнопки: "Одобрить" / "Запросить доп. документы" / "Отказать (с причиной)"

---

### А2: Верификация документов и выдача доступа

**После нажатия "Одобрить":**
1. `ClinicOnboardingRequest.status = "approved"`
2. `ClinicOnboardingRequest.reviewer_id = superadmin.id`
3. Если Путь А (привязка): `UserClinic(user_id, clinic_id, staff_role="owner")` + `user.roles += ["clinic_owner"]`
4. Если Путь Б (новая): сначала суперадмин создаёт `Clinic` в БД → затем привязка
5. Владелец получает email: "Ваша заявка одобрена. Войдите в личный кабинет."

**После "Запросить документы":**
1. `status = "docs_required"`
2. Поле `rejection_reason` = комментарий суперадмина
3. Email владельцу: "Для продолжения рассмотрения требуются: [список документов]"

---

### А3: Модерация контента (отзывы, профили)

**Отзывы:**
- Очередь: новые отзывы в статусе `pending_moderation`
- Проверка: нет ли спама, фейков, личных данных, нецензурной лексики
- Действия: Опубликовать / Редактировать (убрать личные данные) / Отклонить
- Auto-moderation (в будущем): нейросетевая фильтрация

**Профили врачей:**
- Новые фото врачей → проверка (медицинский вид, нет рекламы)
- Изменения в биографии → spot-check

### А4: Управление подписками и оплатой

**Тарифный менеджер:**
- Список всех клиник с их тарифом
- Ручная смена тарифа (для переговоров / промо)
- Выставление счёта вручную
- Статусы: active / past_due / suspended / cancelled

**Биллинг:**
- Интеграция с ЮKassa / Tinkoff (платёжный шлюз)
- Автосписание: каждый месяц в дату подключения
- При неоплате: предупреждение → ограничение функций → суспенд

## ЧАСТЬ 9 — Узкие места и риски {#часть-9}

### Risk 1: Ручная верификация клиник → bottleneck
**Описание:** Каждая заявка клиники обрабатывается суперадмином вручную. При росте >20 заявок в день это станет узким местом.

**Последствия:** Задержка онбординга → клиники уходят к конкурентам → потеря выручки.

**Митигация:**
- Интеграция с API ФНС (проверка ИНН/ОГРН автоматически)
- Интеграция с базой Росздравнадзора (проверка лицензии автоматически)
- Авто-одобрение если все автопроверки прошли + docs загружены
- SLA: "Рассмотрим в течение 24 часов"

---

### Risk 2: Фейковые клиники и врачи
**Описание:** Злоумышленник может создать фейковую клинику, собирать предоплату за записи.

**Последствия:** Репутационные риски для MEDAS, юридические проблемы.

**Митигация:**
- Верификация по документам ОБЯЗАТЕЛЬНА перед публикацией клиники
- `Clinic.is_verified = False` по умолчанию → не показывается в поиске
- Суперадмин подтверждает перед публикацией
- Бэдж "Верифицированная клиника" на странице
- Телефон поддержки MEDAS виден пациентам

---

### Risk 3: Безопасность ролей — эскалация привилегий
**Описание:** Пользователь может попытаться получить роль `clinic_owner` или `superadmin` без верификации.

**Потенциальные векторы:**
- Прямой запрос PATCH /users/me с `roles: ["superadmin"]`
- Манипуляция с JWT (если секрет слабый)
- Обход верификации в onboarding

**Митигация:**
- `roles` НИКОГДА не обновляется через публичный API напрямую — только через специфические endpoint'ы
- `superadmin` роль добавляется только из БД вручную (нет API для этого)
- JWT подписан сильным HMAC-SHA256 ключом (>256 бит энтропия)
- Все изменения ролей логируются в `audit_log`

---

### Risk 4: Инвайт-ссылки врачей / сотрудников — перехват
**Описание:** SMS с ссылкой `/invite/TOKEN` можно перехватить (MITM, SIM-swap).

**Последствия:** Злоумышленник принимает инвайт от чужого имени.

**Митигация:**
- TTL токена 7 дней (минимально необходимый)
- Токен одноразовый (при accept сразу инвалидируется)
- После принятия — SMS уведомление реальному врачу: "Ваш аккаунт привязан к клинике X"
- Врач может отвязаться из ЛК

---

### Risk 5: Утечка персональных данных пациентов
**Описание:** Медицинские данные — наиболее чувствительная категория по 152-ФЗ.

**Последствия:** Штрафы РКН, потеря доверия, уголовная ответственность.

**Митигация:**
- TLS 1.3 везде
- Шифрование БД (PostgreSQL pgcrypto для sensitive fields)
- httpOnly cookies для JWT (не доступны JS)
- Логи не содержат телефонов и медданных
- Доступ к медкартам — только врач и пациент (не клиника-admin)
- GDPR/152-ФЗ compliance: право на удаление данных

---

### Risk 6: Конкурент клонирует платформу
**Описание:** MEDAS — B2B2C маркетплейс с относительно простой архитектурой. Барьер копирования низкий.

**Митигация:**
- Скорость роста > скорость копирования
- Network effect: больше клиник → больше пациентов → лучший поиск
- Данные (история записей, отзывы) — трудно скопировать
- Партнёрства с клиниками на ранних этапах (эксклюзивные договоры)

---

### Risk 7: no-show пациентов (неявка)
**Описание:** Пациент записывается и не приходит → клиника теряет выручку, слот занят зря.

**Последствия:** Клиники недовольны платформой, снижают конверсию.

**Митигация:**
- SMS/email напоминание за 24ч и за 2ч до приёма
- Опциональный штраф за неявку (клиника настраивает)
- Система репутации пациента (много no-show → предупреждение)
- Онлайн-предоплата снижает no-show на ~40%

---

### Risk 8: Масштабирование при росте нагрузки
**Описание:** Текущий стек — один VPS (85.239.44.14). При росте до 10 000 MAU — возможны проблемы.

**Митигация:**
- Redis кэш для поиска (уже есть)
- CDN для изображений (CloudFlare)
- Горизонтальное масштабирование FastAPI через Docker (несколько реплик)
- Read replica PostgreSQL при нагрузке >500 RPS
- Monitoring: Grafana + Prometheus

---

### Risk 9: Ошибки в алгоритме расписания
**Описание:** Двойная запись к врачу (два пациента в один слот).

**Последствия:** Скандал, жалобы, потеря клиники.

**Митигация:**
- `UNIQUE constraint` на `(doctor_id, scheduled_at)` в таблице appointments
- Оптимистичная блокировка при создании записи (SELECT FOR UPDATE в транзакции)
- E2E тест: попытка двойной записи в один слот

---

### Risk 10: Зависимость от smsc.ru
**Описание:** Вся авторизация завязана на одного провайдера звонков.

**Последствия:** При падении smsc.ru — никто не может войти.

**Митигация:**
- Fallback провайдер (звонок.ru или МТТ) при ошибке smsc.ru
- Мониторинг доступности smsc.ru
- В крайнем случае — fallback на SMS OTP (не звонок)
- Alert при >5% ошибок OTP в течение 5 минут
